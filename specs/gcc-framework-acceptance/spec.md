# Lab Equipment Checkout Framework Acceptance Specification

## Scenario Summary

Lab Equipment Checkout is an isolated Framework Acceptance scenario for validating the Power Platform VS Code Starter against a permanent GCC environment. A lab coordinator reviews checkout requests, approves them, issues assets, and records returns without changing existing isolated Contoso components.

## Scope And Safety

- Wizard mode: `framework-acceptance`
- Environment: Power Platform VS Code Starter - GCC
- Environment URL: `[APPROVED_GCC_ENVIRONMENT_URL]`
- Environment lifecycle: permanent; it must not be reset or deleted
- Solution: `LabEquipmentCheckoutAcceptance20260826`
- Publisher: create permanent `PowerPlatformVSCodeStarter` publisher with prefix `ppvs`
- Solution prerequisite: create unmanaged `LabEquipmentCheckoutAcceptance20260826` under that publisher
- Source tag: `ppvs-acceptance-20260826`
- Cleanup: the permanent publisher is always excluded; all other cleanup is prohibited unless separately and explicitly approved
- Current authorization: credential-free local preview only; authentication, query, apply, export, and cleanup are not authorized

## Users And Top Tasks

| Persona | Task | Frequency | Entry table/view | Expected outcome | Owner | Done definition |
| --- | --- | --- | --- | --- | --- | --- |
| Lab coordinator | Review and approve a checkout request | Daily | `ppvs_checkoutrequest` / Active Checkout Requests | Request is ready to issue or clearly declined | Lab operations owner | Decision and lifecycle stage are saved |
| Lab coordinator | Issue an available asset | Daily | `ppvs_checkoutrequest` / Active Checkout Requests | Asset is linked to an approved request and shown as issued | Lab operations owner | Request reaches Issue and asset availability is updated |
| Lab coordinator | Record an asset return | Daily | `ppvs_checkoutrequest` / Active Checkout Requests | Request is completed and asset is available again | Lab operations owner | Actual return date is recorded and lifecycle reaches Return |
| Lab supervisor | Review lifecycle and availability | Weekly | Lifecycle and Availability dashboard | Active requests and available assets are visible with drill-through | Lab operations owner | Dashboard totals reconcile to underlying records |

The table builder also creates the required primary name column `ppvs_name` on each custom table.

### Relationships to create

- ppvs_checkoutrequest (referencing) -> ppvs_labasset (referenced)
- Cardinality: N:1 from Checkout Request to Lab Asset; Lab Asset has 1:N Checkout Requests
- Requiredness: application required on Checkout Request
- Status: new
- Delete behavior: Restrict
- Other cascade behavior: NoCascade
- Supported surface: checkout form, active-request drill-through, lifecycle/availability reporting, and history preservation

## Required Experience

- Checkout Request is the review app entry point.
- Active Checkout Requests is the default landing view.
- Checkout Request Main exposes request identity, asset, requester, lifecycle, approval, date, and source-tag fields.
- Lab Asset Main exposes asset identity, category, availability, and source-tag fields.
- The review app navigation starts with Checkout Request and also exposes Lab Asset.
- The lifecycle and availability dashboard shows active requests, requests by lifecycle stage, and assets by availability, with drill-through to records.

## Business Process Flow

- Display name: Lab Equipment Checkout Lifecycle

- Exactly 3 Lab Asset records and 5 Checkout Request records are planned.
- Every record carries `ppvs_acceptancesourcetag = ppvs-acceptance-20260826`.
- Hero record: `LECA-20260826-001 — Full Review-to-Return Journey`.
- Data is synthetic and contains no personal, customer, or production information.
- Reruns use deterministic natural keys plus the source tag and must not create uncontrolled duplicates.
- Standard reused tables are not seeded.
